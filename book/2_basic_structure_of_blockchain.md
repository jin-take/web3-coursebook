# 第2章 ブロックチェーンの基本構造 ★重要

ブロックチェーンは、取引の集合を一定の単位にまとめ、それらを順序付けて共有するデータ構造です。本章では、ブロック、チェーン、**Merkle Tree**という三つの要素から、記録がどのように検証可能になるのかを学びます。

## この章の学習目標

- Block Header、Transaction群、Block Hashの関係を説明できる。
- Previous Block Hashによる連結と、Consensusによる改ざんコストを区別できる。
- Merkle Proofを使うと、全データなしで包含を検証できる理由を説明できる。

> **最重要ポイント:** 改ざん耐性はハッシュの連結だけでは成立しません。**データ構造による改ざん検知**と、**Consensusによる履歴書き換えコスト**が組み合わさって成立します。

## 2.1 ブロック

### 2.1.1 ブロックとは

ブロックは、一定期間に受け付けられた複数のトランザクションと、その集合を説明するメタデータをまとめたものです。帳簿の1ページに例えられますが、各ページが暗号学的に前のページと結び付いている点が特徴です。

### 2.1.2 ブロックヘッダー

**ブロックヘッダー**には、前のブロックのハッシュ、トランザクション群を要約する**Merkle Root**、時刻や合意形成に必要な値などが格納されます。具体的な項目はブロックチェーンごとに異なります。

ヘッダーはブロック全体より小さいため、ブロックの識別やチェーンの検証を効率よく行うために利用されます。

### 2.1.3 トランザクション

トランザクションは、資産の移転やスマートコントラクトの呼び出しなど、状態を変更する要求です。送信者の署名や宛先、金額、手数料に関する情報を含み、ノードがルールに従って有効性を検証します。

有効なトランザクションでも、ブロックに収録されるまでは確定していません。混雑や手数料設定によっては、収録まで時間がかかったり破棄されたりします。

### 2.1.4 ブロックの識別

多くのブロックチェーンでは、ブロックヘッダーをハッシュ化した値をブロックハッシュとして利用します。内容が少しでも変わればハッシュが変わるため、同じ高さに候補が複数ある場合も区別できます。

ブロック番号またはブロック高はチェーン上の位置を示しますが、それだけではブロックを一意に特定できない場合があります。厳密な識別にはブロックハッシュを使います。

## 2.2 チェーン構造

### 2.2.1 Previous Block Hash

各ブロックは、ヘッダー内に直前のブロックのハッシュを保持します。この参照によって、ブロックは生成順に連結され、途中の記録を変更すると後続ブロックとのつながりが崩れます。

### 2.2.2 Genesis Block

**Genesis Block**は、チェーンの起点となる最初のブロックです。参照すべき前のブロックが存在しないため、プロトコル内で特別に定義されます。初期残高やネットワーク設定が含まれる場合もあります。

### 2.2.3 ブロックの連結

新しいブロックは、合意形成ルールの下で選ばれた直前のブロックを参照して追加されます。ネットワーク遅延などによって一時的に複数の枝が生じることがありますが、プロトコルの規則に従って正規の履歴が選ばれます。

このため、チェーンは常に単純な一本線とは限りません。最新ブロックに近い取引ほど履歴の選択による影響を受けやすく、確認数や**Finality**が重要になります。

### 2.2.4 改ざん耐性

過去のトランザクションを変更すると、そのブロックのMerkle Rootとブロックハッシュが変わり、後続するすべての参照を作り直す必要があります。さらに正規チェーンとして受け入れさせるには、合意形成上の条件も満たさなければなりません。

したがってブロックチェーンは「書き換えが絶対に不可能」なのではなく、参加者と計算資源やステークによって、過去へさかのぼるほど書き換えコストが高くなる仕組みです。

## 2.3 Merkle Tree

*図2-1：Transaction Cの存在を検証するために必要なHashと、Merkle Rootまでの再計算経路*

### 2.3.1 Merkle Treeの構造

Merkle Treeは、複数のデータのハッシュを葉とし、隣接するハッシュを組み合わせて再度ハッシュ化する処理を上位へ繰り返す木構造です。最終的に一つのルートハッシュへ集約されます。

トランザクションが一つでも変わると、その葉からルートまでの値が変わります。この性質により、大量のデータを一つの短い値で要約できます。

### 2.3.2 Merkle Root

Merkle RootはMerkle Treeの最上位にあるハッシュです。ブロック内のトランザクション集合と順序を代表し、多くの場合ブロックヘッダーに保存されます。

ルート自体から個々のトランザクションを復元することはできませんが、提示されたトランザクションがその集合に含まれていたかを検証できます。

### 2.3.3 データ存在証明

あるトランザクションの存在を証明するには、その葉からMerkle Rootまでの計算に必要な兄弟ハッシュだけを提示します。検証者はそれらを順に組み合わせ、既知のMerkle Rootと一致するか確認します。

この証明はMerkle ProofまたはInclusion Proofと呼ばれます。ブロック内の全トランザクションを取得せずに包含を確認できるため、軽量クライアントでも利用できます。

### 2.3.4 検証効率

Merkle Treeでは、データ数が増えても証明に必要なハッシュ数は対数的にしか増えません。例えば葉が約100万件でも、経路上で必要なハッシュはおよそ20段です。

ただし、包含証明はトランザクションの存在を示すものであり、そのトランザクション自体の正当性やブロックが正規チェーンに属することまでは単独で保証しません。

## 検定対策：構造を読み解く

### Blockを構成する情報

| 要素 | 主な役割 | 変更した場合 |
|---|---|---|
| Transaction | 状態変更の要求 | Transaction HashやMerkle Rootが変わる |
| Merkle Root | Transaction集合の要約 | Block HeaderとBlock Hashが変わる |
| Parent Hash | 前Blockへの参照 | 過去との連結が切れる |
| Timestamp | 時刻に関する情報 | Header Hashが変わる |
| Consensus用データ | 提案者、難易度、Nonce等 | Blockの有効性やHashが変わる |
| Block Hash | Headerの識別値 | 内容を一意に追跡する基準が変わる |

Headerの具体的項目はChainごとに異なります。例えばPoWのNonceと、PoSのValidator署名は目的や形式が異なります。検定では特定Chainの項目を全Blockchain共通と誤認しないことが重要です。

### 改ざんを試みたときに起きる連鎖

1. 過去のTransactionを変更する。
2. そのTransactionのHashとMerkle Rootが変わる。
3. Block HeaderとBlock Hashが変わる。
4. 次のBlockが保持するParent Hashと一致しなくなる。
5. 後続Blockをすべて作り直し、正規Chainを上回るConsensus上の重みを得る必要が生じる。

**ハッシュは変更を検出しますが、変更そのものを物理的に禁止しません。** 正規履歴としてネットワークに受け入れさせにくくするのがConsensusと経済的コストです。

### Merkle Proofの計算例

4件のTransactionを `A, B, C, D` とし、それぞれのHashを `hA` から `hD` とします。上位では `hAB = H(hA || hB)`、`hCD = H(hC || hD)` を計算し、Rootを `H(hAB || hCD)` とします。

`C` の包含を検証するために必要なのは、`C` 本体に加えて兄弟の `hD` と反対側の枝 `hAB` です。検証者は `hC` と `hD` から `hCD` を再計算し、さらに `hAB` と組み合わせて既知のRootと比較します。**全4件を受け取らずにCの包含を検証できる**ことが要点です。

データ数を `n` とすると、平衡な二分Merkle TreeでProofに必要なHash数は概ね `log2(n)` です。一方、全データの正当性を初めから検証するには、各TransactionとBlockのConsensus上の有効性も必要です。

### よくある誤解

- Block Numberは位置を示すが、一時分岐中のBlockを一意に識別するには**Block Hash**が必要。
- Merkle Proofは包含を証明するが、**そのデータが現実世界で真実であること**は証明しない。
- Genesis Blockにも通常の前Blockは存在しない。起点はProtocolで特別に合意される。
- Chainが長いことだけで正規とは限らない。PoWでは累積作業量、PoSでは投票や確定規則などを使う。

### 確認問題

1. 過去のTransactionを変更してもMerkle Rootだけを元の値に保てば改ざんは検出されない。正しいか。
2. Light ClientがあるTransactionの包含を検証するために必要な代表的データは何か。
3. Block HeightとBlock Hashの違いを述べよ。

#### 解答と解説

1. **通常は誤り。** 安全なHash関数で同じRootを意図的に作ることは衝突耐性により困難。
2. **対象Transaction、Merkle Proof、信頼できるBlock Header。** さらにHeaderが正規Chainに属することの検証が必要。
3. **HeightはChain上の位置、Hashは内容に基づく識別子。** 分岐時には同じHeightへ異なるBlockが存在し得る。

## まとめ

ブロックは取引をまとめ、**Previous Block Hash**が履歴を連結し、Merkle Rootが取引集合を効率よく要約します。これらのデータ構造とネットワークの合意形成が組み合わさることで、ブロックチェーンの検証可能性と改ざん耐性が成立します。
